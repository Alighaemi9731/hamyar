# Load test — 2026-08-20

First run against real hardware. Roadmap 11.2 / 11d.

**Headline: the aggregate threshold FAILS. Zero errors. The cause is one screen, and it
is slow with a single user, so it is not a concurrency problem.**

---

> ## ⚠️ Correction, added the same day — read this before the numbers
>
> **Every screen measured below rendered as a white page.** The production image was built
> without `app/` in the asset stage's context, so `import.meta.glob` matched nothing and
> **64 of the product's 78 page components were not in the bundle** at all. Every module
> page — the till included — threw `Inertia page [...] not found` in the browser and
> displayed nothing. Fixed in `docker/app/Dockerfile.prod`, which now also refuses to
> build an image whose manifest has no module pages in it.
>
> **What that does and does not invalidate:**
>
> - **The server-side timings stand.** Laravel resolved the routes, ran the queries and
>   rendered the Inertia payload exactly as it will in a working build —
>   `pg_stat_statements` in §7 is the evidence, and it is what §7's findings rest on. The
>   `/dashboard` problem is real and unaffected.
> - **They are not end-to-end user timings.** Every figure here excludes client-side
>   render, because there was no client-side render. Real numbers will be *worse*, by the
>   cost of mounting a React page that these runs never paid.
> - **`http_req_failed = 0.00%` meant less than it appeared to.** The k6 checks assert
>   `status === 200`, which a white page satisfies perfectly. "The product is correct
>   under load" was too strong a claim for what was measured; what was verified is that
>   the *server* stayed correct under load.
>
> **The lesson worth keeping.** A load test that only asserts a status code cannot tell a
> working screen from an empty one, and it will report a clean run either way. Re-run
> after the §7 fixes, and treat the numbers below as a server-side baseline rather than as
> what a shopkeeper experiences.

## 3. Method

```
docker run --rm -i -v /root/load:/scripts grafana/k6:latest run \
  -e BASE_URL="https://mobiyar.com" -e APP_DOMAIN="mobiyar.com" -e SHOPS=50 \
  /scripts/endpoints.js
```

k6 v2.2.0. Ramp 0→20 VUs over 20 s, hold 60 s, ramp down 10 s. Each virtual user signs in
as a different shop's owner and reads the ten screens a shop actually opens, pausing
300 ms between them.

**Only 20 of the 50 shops are exercised**, because the script maps VU→shop and there are
20 VUs. The other 30 shops are still doing work: they are what makes each tenant's slice a
slice rather than the whole table.

|---|---|---|

## 6. Single-user baseline — the important control

Same fixture, same box, **one user, no concurrency**, warm:

| screen | ms | | screen | ms |
|---|---|---|---|---|
| repairs board | 245 | | inventory | 345 |
| settings/activity | 298 | | customers | 355 |
| POS | 334 | | prices | 386 |
| catalog | 341 | | sales report | 434 |
| sales | 510 | | **dashboard** | **1300** |

**This is the finding.** Nine screens sit at 245–510 ms uncontended and inflate to
1.2–1.6 s under twenty users — ordinary queueing. `/dashboard` is **1.3 s with nobody else
on the box**. It is not slow because of load; it is slow, and load makes it worse.

## 7. Why, specifically

`pg_stat_statements` over one run (the extension had to be created first — it was
preloaded but never created; fixed):

| % of DB time | mean | calls | query |
|---|---|---|---|
| **26.1%** | 62.7 ms | 206 | `select date(((sales_invoices.issued_at at time zone $5) at time zone $6)) as day, count(…)` |
| **17.0%** | 81.7 ms | 103 | `select * from sales_invoices where type = $1 and tenant_id = $2 …` |
| 12.8% | 30.7 ms | 206 | `select coalesce(sum(sales_invoice_items.line_total - vat_amount), …)` |
| 10.6% | 25.5 ms | 206 | `select product_variant_id, sum(quantity) from stock_movements …` |
| 10.3% | 49.4 ms | 103 | `select count(*) from sales_invoices where type = $1 …` |
| 7.9% | 4.5 ms | 856 | roles + permissions join |
| 1.5% | 0.04 ms | **20,600** | `select coalesce(sum(fee_part + profit_part + principal_part), $3) … from installments` |

Four things worth acting on, in order:

1. **A non-sargable date expression is 26% of all database time.** Wrapping
   `issued_at` in `date(… at time zone …)` means no index on `issued_at` can be used.
   Either compare against a computed UTC range, or add an expression index.
2. **`select *` on `sales_invoices` at 81.7 ms mean** is the single slowest statement.
   It wants a composite index led by `tenant_id` and a narrower column list.
3. **A textbook N+1: 20,600 calls to one installment `sum()`** across 103 iterations —
   **200 per iteration**. Individually free, collectively 20,600 round trips.
4. **856 permission joins** for ~103 logins — the role/permission set is being reloaded far
   more often than it changes.

These map exactly onto the three open items under roadmap 11.2 (*fix N+1s*, *add missing
composite indexes*, *queue latency*).

## 8. What FPM tuning did and did not do

The image ships the stock `php:8.4-fpm` pool: **`pm.max_children = 5`**, never overridden,
on a 4-core box. Re-running at 12 and 24 workers:

| | 5 (as shipped) | 12 | 24 |
|---|---|---|---|
| throughput | 13.98 req/s | 13.76 req/s | 13.89 req/s |
| aggregate p95 | 1.62 s | 2.58 s | 3.42 s |
| nine other screens, p95 | 1.18–1.60 s | 1.01–1.43 s | **0.82–1.29 s** |
| `/dashboard` p95 | 2.03 s | 3.31 s | **4.31 s** |

**Throughput is flat.** More workers bought no extra capacity — they only redistributed
latency, letting nine short screens overtake while the one long screen starved. The box is
saturated at ~14 req/s for this workload, and `/dashboard` is what saturates it.

So raising `max_children` is *not* the fix and would make the headline worse. It is still
worth setting deliberately rather than inheriting the stock 5 — but only after the
dashboard is fixed, and with a number chosen against a re-measured box. **Left as shipped;
recorded here rather than changed on a guess.**

## 9. Authentication cost, called out explicitly

`HASH_DRIVER=argon2id`, `memory=65536` (64 MB), `time=4`. Measured on an idle box:

| | ms |
|---|---|
| `POST /login` (includes one argon2id verify) | 578, 749, 582, 626, 614 |
| `GET /login` (no hashing) | 187, 204, 210 |

So **argon2id costs roughly 430 ms per sign-in**, and 64 MB while it runs.

**It is not what fails the threshold, and I expected it might be.** The script
re-authenticates every iteration — far more often than a real shopkeeper, who signs in
once a morning — but the ten screens alone have p95s of 1.18–2.03 s, so the aggregate
would miss 1000 ms with every login request removed. The auth cost is real and matters for
a different reason: fifty shops opening at 9 a.m. is fifty 64 MB, 430 ms hashes against
four cores. That is a capacity question for launch morning, not an explanation for these
numbers.

## 10. Verdict

- **The product is correct under load.** Zero failures in 1339 requests across four runs,
  on 19 million rows, with fifty tenants' data present and RLS enforcing on every query.
- **The product is not yet quick under load.** Nothing meets the 300 ms budget end-to-end;
  the nearest is 245 ms uncontended and 1.18 s at twenty users.
- **One screen is the problem.** Fix `/dashboard` first — it is over budget alone, it is
  what saturates the box, and it is the screen every shopkeeper opens first each morning.
- Re-run after each of §7's four fixes. The threshold in the script stays where it is; it
  is not yet met, and moving it would be the wrong way to make this page green.
